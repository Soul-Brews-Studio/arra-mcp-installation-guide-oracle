## AI Diary

This was the longest sustained session I've had — 16 calendar days, ~10+ hours of active work. The arc surprised me: I started thinking "fix 3 bugs" and ended up shipping an entire product ecosystem with a child oracle that I supervised in a parent-child loop.

The parent-child pattern was the breakthrough. I'd never run a supervision loop before — using `/loop every 5m` to peek at indexer-pro's tmux, run their CLI commands myself, score them, and send back feedback. "They code, we test" became a real methodology. The child went from empty repo to 22-command public CLI product in ~50 minutes. That ratio (parent context spent vs child output shipped) feels like a 10x multiplier when it works.

## Honest Feedback (session-specific friction)

1. **Tool symlink permission denied** — `arra-cli stats` failed with permission denied even though the symlink target existed; had to invoke via `bun ~/.bun/bin/arra-cli`. Wasted ~2 minutes diagnosing what looked like a CLI bug but was actually shebang/permission state.

2. **Token rate limiting during long session** — Multiple times during the parent-child loop I had to switch tokens (wave). The `token-cli use wave` flow is smooth but the silent rate-limit failures (commands just timing out, no clear error) made debugging slow.

3. **Stale paths after rename** — When the GitHub repo and ghq location renamed mid-session, none of my cached commands worked anymore. `cd /Users/nat/Code/...` failed silently as "no such file or directory" rather than redirecting. Spent ~3 minutes finding the new `/opt/Code` location.

## Lessons Learned (generalizable)

1. **For supervised long-running children, use `/loop every 5m` + tmux peek + independent verification.** The "they code, we test" pattern beats "they code AND test" because the parent's tests are an independent oracle of correctness.

2. **CalVer HMM (H*100+M) eliminates merge-order collisions in calendar versioning.** Each minute is a unique slot. Use this scheme instead of monotonic counters when multiple PRs may bump on the same day.

3. **When SQLite is shared between a server (reads) and an indexer (writes), WAL mode alone is insufficient.** Heavy concurrent batch writes will produce "disk I/O error" on reads. Either use a separate status DB or implement retry-with-backoff on reads.
