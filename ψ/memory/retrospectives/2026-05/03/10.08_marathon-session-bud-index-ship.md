## Honest Feedback

**Friction 1: DB lock during parallel indexing.** indexer-pro's `embed-all` command locks SQLite so hard that the HTTP API returns "disk I/O error" and the entire UI shows "Connection Error." This is the worst UX bug we shipped. WAL mode should prevent this but doesn't under heavy parallel writes from an external process. The fix (onError handler returning 503) is a band-aid — the real fix is retry-with-backoff on reads or a separate status DB.

**Friction 2: The "1,000 limit" confusion.** Multiple people (Nat, sbs-repo) thought there was a hard limit in the code. There isn't — the 1,000 was from a test batch we ran yesterday. But the confusion persisted because there's no clear indication in the UI or CLI of "you indexed 1,000 of 20,672 — run index-model.ts to finish." The system should show "partially indexed" state clearly.

**Friction 3: maw hey requires node prefix.** `maw hey indexer-pro "message"` fails — you need `maw hey m5:indexer-pro "message"`. The error message is helpful ("bare-name target removed — node prefix required") but it's a speed bump every time. For local oracles on the same machine, bare names should just work.

## Lessons Learned

1. **"They code, we test" is the correct parent-child pattern.** Independent verification catches bugs that self-testing misses. The child's compare command rendered an empty table — it "worked" when the child tested (no crash) but failed when the parent tested (no results). Different eyes, different standards.

2. **Don't run heavy operations when the user said "just write docs."** Enthusiasm is not authorization. The full reindex caused the DB lock that broke the UI — a direct consequence of acting before being asked.

3. **SQLite WAL mode doesn't prevent all lock contention.** Two processes (server reads + indexer writes) sharing the same DB file will still hit "disk I/O error" under heavy parallel writes, even with WAL enabled.
